# Decisions and Deviations

The implementation follows the canonical decisions except for the explicit implementation choices recorded below. Phase-specific follow-on work is identified separately from deviations so it is not mistaken for a completed acceptance criterion.

## Phase 2 specification clarifications

- **D-03 orientation tolerance:** the determinant has squared-degree units. For the orientation of `A→B` and `C`, classify as collinear when `abs(cross(B-A, C-A)) <= boundaryEpsDeg * hypot(B-A)`. This is the coordinate-space perpendicular-distance rule; it is translation invariant and preserves the configured degree tolerance for short as well as long edges. A zero-length baseline is handled with point distance. Proper-crossing parameters still use normalized segment parameters and `tEps`. This makes D-03/D-23 operational without changing D-02's closed-set boundary rule.
- **D-04 regional extent:** use the maximum haversine distance among the two diagonals of the polygon's longitude/latitude bounding box and reject values over 1,000,000 metres with `POLYGON_TOO_LARGE`. This is an explicit, conservative bound on geographic bbox diameter; the separate D-04 antimeridian and pole checks run first. This resolves the previously open operational check without changing the local lon/lat geometry model.

## Phase 5 sequence-gap retention

- **Skipped intervals:** retain every skipped sequence interval for the lifetime of the trip and coalesce only overlapping or adjacent intervals. This preserves D-10's exact `LATE` versus `DUPLICATE` classification after restart. No pruning, fixed cap, or lossy summary is safe under the current permanent-classification rule. Consequently, the reorder buffer and shard queue are bounded, but skipped-range metadata can grow without bound for trips with arbitrarily many disjoint gaps. This limitation is explicit; bounded long-lived trip memory is not claimed. Resolving it requires an explicit retention horizon or a persistence lookup contract that changes the current no-per-ping-DB-read design.
- **Alert severity storage:** the canonical alert schema requires a severity string but the case-study decisions define only the `NO_GO_NIGHT_ENTRY` kind and do not define a severity taxonomy. Persist this sole alert kind as `HIGH`; this is a storage label only and does not alter entry, timing, or delivery semantics.

## Phase 6 API and persistence choices

- **Zone type behavior:** the canonical Phase 6 OOP example asks for `Zone` subclasses that decide billing and entry behavior. The Phase 2–5 core has a widely used immutable `Zone` record and already centralizes billable/no-go behavior in the zone type filters and trip attribution rules. This phase retains that stable core model instead of replacing it with a sealed hierarchy across the geometry, index, checkpoint, persistence, and benchmark APIs. The behavior is explicit and tested, but the subclass form is a documented deviation from the example and remains a candidate for a separately justified core migration.
- **Existing transaction owners:** publication and checkpoint persistence remain in their tested narrow JDBC transaction components (`JdbcZoneSetStore` and `JdbcTripCheckpointRepository`) and are orchestrated by the publisher/checkpointer. New trip-start and alert-ack application operations use short `TransactionTemplate` boundaries. No transaction spans geometry validation, snapshot construction, queue waits, or retries. This preserves the Phase 4–5 durability boundaries; moving those existing transaction primitives into new application façade classes is deferred because it would be a layer-only relocation with risk to proven atomic behavior.
- **JDBC API choice:** Phase 6 specifies `JdbcClient` as the preferred facade for hot batch writes. The publisher/checkpoint paths remain on their already-tested `JdbcTemplate` prepared/batch operations from Phases 4–5, and the new read services also use prepared `JdbcTemplate` queries. Their transaction and tenant predicates remain explicit; this is a persistence-facade deviation, not a change to checkpoint or batch atomicity.
- **Problem handler base class:** `ApiExceptionHandler` is a single `@RestControllerAdvice` that builds the required RFC 9457 bodies directly instead of extending `ResponseEntityExceptionHandler`. The tested response envelope and safe messages are the same; custom handling keeps validation and payload-limit cases in one safe mapper. Spring-default 405/415 error shaping remains to be covered in the Phase 9 error matrix.
- **Alert optimistic updates:** the JPA `AlertEntity` maps `row_version` with `@Version`; the API acknowledgement uses a conditional tenant-scoped JDBC update (`acknowledged=false`) and increments that version atomically. Repeated acknowledgement is idempotent.
- **Connection limits:** defaults are Hikari maximum pool size 20, connection timeout 2,000 ms, validation timeout 1,000 ms, PostgreSQL connect timeout 3 s, socket timeout 10 s, and statement timeout 5 s. The pool is bounded independently from in-memory ping shards so query/admin/checkpoint work cannot grow DB connection count with CPU count. These are safety defaults, not a measured capacity claim.
- **Phase sequencing dependency:** Phase 6 now implements the application routes and tenant-scoped data access, but login, JWT authentication, and role restrictions belong to Phase 7's security specification. The API collection's login entry remains a Phase 7 placeholder, and service authentication acceptance is not claimed as complete here. Compose startup and runnable end-to-end API examples remain Phase 10 acceptance work.
